# 功能设计 V2：镜头时长驱动的自动配乐（Shot-Duration Driven BGM）

> **实施状态：P1–P5 已全部落地**（见「七、实施计划」的状态列与实测数据表）。
> 对应前端版本 **v4.0**，自检脚本 `tools/selftest_v4.js`（59 项断言）。
>
> **需求原话**：「根据视频时长，然后再镜头切分点的时长查看镜头去配乐，并配合剧本规则兜底。」
>
> 即三段决策：**① 视频总时长 → ② 逐镜头（含每个镜头自己的时长）→ ③ 配乐 + 剧本规则兜底**。
>
> V1 文档（同目录旧版）是通用设计；本 V2 针对「镜头时长」这个核心输入重写数据流与算法。

---

## 〇、先说清楚：现在哪里不符合这个需求

现有前端（`web/index.html`）确实检测了镜头切点，但**把镜头信息在下一步就丢掉了**：

| 环节 | 现在怎么做 | 问题 |
|---|---|---|
| 镜头切点 | `detectScenes` 抽帧帧差 → `cuts[]` | 只产出**切点时刻**，没产出**每个镜头的时长** |
| 短段合并 | `mergeShortSegments`：短于 4s 的镜头**直接删掉**，最多留 12 段 | 快切镜头（恰恰是节奏信息最强的）被抹平；镜头结构丢失 |
| 时间↔剧本 | `ratio = i/(N-1)` → `scIdx = floor(ratio × 场数)` | **纯按比例硬凑**：第 3 个时间段就配第 3 场，和时间轴真实对不上 |
| 情绪判定 | 每段取**中点一帧**给 VLM | 一个 30 秒的镜头只看 1 帧；镜头内部情绪变化看不到 |
| 换曲点 | 相邻段情绪余弦 < 0.7 就合并，否则断开 | 换曲点**完全由情绪决定**，可能落在镜头中间 → 画面没切、音乐先换，违和 |
| 选曲 | 只看 1024 维情绪向量 + 硬过滤人声 | **时长/节奏/能量一律没参与**；靠 `alignToDuration` 事后硬拉伸裁剪 |
| 段数 | `MAX_MUSIC_SEGMENTS = 3` 硬限制 | 与"覆盖全片镜头结构"目标冲突 |

**一句话**：现在是「按剧本比例切时间 → 每段选一首」，而需求是「**按镜头切分结构 → 每个镜头有时长 → 按时长与情绪共同决定乐段**」。

## 一、核心概念（先把词定义死）

| 词 | 定义 | 来源 |
|---|---|---|
| **镜头 shot** | 相邻两个画面硬切点之间的一段。**不可再分的最小单位** | M1 检测 |
| **镜头时长 shot.dur** | `t1 - t0`。本方案的**一等公民输入** | M1 检测 |
| **ASL** | Average Shot Length，全片平均镜头时长 = 视频总时长 / 镜头数 | M1 派生 |
| **CPM** | Cuts Per Minute，每分钟切点数 = 60 / ASL。快剪/慢叙事的分档指标 | M1 派生 |
| **乐段 seg** | 一段**连续播放同一首 BGM** 的区间，由 1..N 个连续镜头组成 | M4 聚合 |
| **换曲点** | 相邻乐段的边界，**必须吸附到镜头切点** | M4 输出 |

关键约束：**乐段边界 ⊂ 镜头切点集合**。音乐永远不在镜头中间换。

## 二、目标数据流

```
视频文件 ──┐
           ├─► M1 镜头检测 ──► shots[] = {t0, t1, dur, 代表帧}
剧本文本 ──┘                      │
                                ├─► M2 镜头↔场 对齐 ──► shot.scriptText / shot.sceneId
                                │
                                ├─► M3 情绪判定 ──► shot.moodVec（规则必算，VLM 增强）
                                │        └─ 规则层：analyzeMood(台词)  ← 兜底，0 成本
                                │        └─ 视觉层：VLM 看代表帧     ← 增强，失败即回落
                                │
                                └─► M4 乐段聚合（DP）──► segments[] = {t0, t1, dur, moodVec, shots[]}
                                          │
曲库索引 ──► M5 选曲打分 ─────────────────┘  score = w1·情绪 + w2·时长 + w3·节奏 + w4·能量
                                          │
                                          └─► M6 拼接（换曲点吸附镜头切点）──► M7 导出
```

## 四、算法细节

### M1 镜头检测（改造点：产出时长 + 提速）

**输出结构**

```js
shot = { i, t0, t1, dur, frames: {head, mid, tail} }
shots[] = [...];  // shots[i].t1 === shots[i+1].t0
```

**提速改造（现状是逐个 seek，全片串行）**

| 改造 | 做法 | 收益 |
|---|---|---|
| 帧数封顶 | `STEP = clamp(videoDur / 160, 0.4, 1.5)` | 视频越长步长越大，总抽帧数恒 ≤ ~160，**不再随时长线性变慢** |
| 抽帧方式 | 优先 `requestVideoFrameCallback` + `playbackRate=4` 边播边采；不支持则回退 seek | 消除逐帧 seek 等待 |
| 双阈值 | 帧差阈值 + **直方图距离**双条件，减少闪光/快速推拉导致的误切 | 切点更准，减少假镜头 |

> 实测基线（本机 Chrome，640×360 合成 webm）：单次 seek ≈ **21 ms**；88.8s 视频按 `STEP=0.6` 需 148 次 seek ≈ **3.1 s**。
> 封顶 160 帧后长视频收益更明显（120s 视频从 200 次 → 160 次）。

**为什么必须保住短镜头**：快切（0.5~2s 一串）本身就是"紧张/冲突"的强信号；现在的 `mergeShortSegments` 把 4s 以下全删了，等于把这个信号扔了。
V2 改为：**不在检测阶段合并**，把"是否合并"推迟到 M4 用情绪 + 时长一起决策。

### M2 镜头↔场 对齐（新增，解决"硬凑"）

剧本先切场（`parseScenes` 已有，靠 `35-1` 场号）。

**粗对齐（默认，0 成本）—— 按"字数权重"而非按段数比例**
```
w_i = 场 i 的正文字数（或对白行数）
场 i 应覆盖的视频区间 = [ Σ_{j<i} w_j / Σw × T , Σ_{j<=i} w_j / Σw × T )
再把该区间内的镜头全部归给场 i
```
比现在的 `i/(N-1)` 准：台词多的场通常拍得更长。

**精对齐（可选开关，用 VLM）**
把镜头代表帧按序分批送给 VLM，让它从"候选场列表"里选，用 **DP** 保证单调不回退（场序不可逆）。成本高，默认关闭。

### M3 情绪判定（**剧本为主，画面补充**）

> **口径于 2026-10-16 正式反转**（用户要求：「情绪弧线要以剧本为主，并根据视频把控节奏」）。
> 原设计是"VLM 优先、规则兜底"，实际会把整条情绪弧线交给单帧画面 ——
> 而画面读不出剧情概念：苦笑与真笑同框、打脸是屈辱还是爽点、跪地是求饶还是隐忍。
> 现在改为**剧本优先**，VLM 降级为"剧本说不出话时才开口"。

```
对每个镜头 shot_i：
  rule = moodRule(shot.scriptText)        ← 剧本规则层，永远先算，0 成本，不会失败
  if (rule.score > 0):                    ← 剧本能判出情绪档 → 一律用剧本
      mood = rule
  elif (VLM 有结果):                       ← 剧本这一场没有任何情绪线索 → 才用画面
      mood = vlmQuery
  else:                                   ← 都没有 → 延续上一镜头 / 默认中性
      mood = 降级链
  shot.moodVec = embedText(mood.query)    ← 1024 维，与索引同空间
```

来源标注：`剧本`(琥珀) / `画面`(绿) / `延续`(靛) / `默认`(灰)，逐镜头可查、段级取众数
（`mainSource` 优先级 剧本 > 画面 > 延续 > 默认）。状态栏给出各来源的镜头计数。

**VLM 仍然照旧调用**（关键镜头 + 4 路并发），只是结果只在剧本无线索处生效 ——
这样"剧本判不出的那几场"依然有画面兜底，且不浪费已有调用。

**"关键镜头"怎么挑（省钱关键）**——不是每个镜头都值得调 VLM：
1. 时长最长的前 K 个（K 默认 6）
2. 规则层情绪得分突变处的镜头
3. 每隔 ⌈n/K⌉ 个镜头的均匀采样
→ 12 段降到 ~6 次 VLM 调用。

**并发**：VLM 调用用 **4 路并发池**（`Promise` 池 + 信号量），12 次串行 → 3 批。

### M4 乐段聚合（核心新增）

**目标**：把 `shots[]` 切成 `segments[]`，同时满足
1. 乐段边界 **必须** 落在镜头切点上（天然满足，因为最小单位就是镜头）
2. 相邻镜头情绪相似 ⇒ 倾向合并（同一首继续播）
3. 边界处"换曲适宜度"要高
4. 每段时长 ≥ `MIN_SEG`（默认 6s）
5. 段数 ≤ `MAX_SEGS`（默认 8）

**换曲适宜度 cutability（本方案的"镜头时长"落地处之一）**

```js
// 镜头越长，画面越"稳"，越适合在这里换音乐；
// 一串快切中换曲会很乱。
function cutability(shots, i) {           // i 为候选边界（shots[i-1] | shots[i] 之间）
  const prev = shots[i-1], next = shots[i];
  let s = 0;
  s += 0.6 * Math.min(1, Math.max(prev.dur, next.dur) / 6);   // 长镜头加分
  s += 0.4 * Math.min(1, (prev.dur + next.dur) / 12);         // 边界两侧总长加分
  if (prev.dur < 2 && next.dur < 2) s *= 0.2;                 // 快切串中几乎不换曲
  return Math.min(1, s);
}
```

**DP 最优分段**（替代现在的贪心）

```
状态：f[k][i] = 前 i 个镜头切成 k 段的代价
转移：f[k][i] = min over j<i { f[k-1][j] + cost(j, i) }

cost(j, i) =
    λ1 · (1 - 段内主导情绪时长占比)        // 段内情绪要纯
  + λ2 · (1 - cutability(shots, j))        // 边界要好换
  + λ3 · segDurPenalty(j, i)               // 段长与曲库可用时长的匹配代价
  + λ4 · [段时长 < MIN_SEG]                // 太短重罚
  + λ5 · longPenalty(段时长)               // 太长该换曲了（>45s 线性增长，60s 封顶 0.7）
```

`segDurPenalty` 直接用曲库时长分布（见 M5）估"这段时长有没有合适的曲子"。
贪心改 DP 的收益：不会因为前几个镜头"恰好相似"就锁死后面所有分段，避免 `MAX_MUSIC_SEGMENTS=3` 那种硬限制带来的怪异结果。

> **λ5 的由来（2026-10-16 实测回归）**：第 48 集 90.8s、剧本只有一场戏 →
> 全部镜头情绪同档 → 段内不纯恒 0 → DP 判"怎么切都白付边界代价" → 整片只配 1 首。
> 尝试把"镜头节奏纯度"加进代价 1 失败：真实视频里快切/中速是**细粒度交错**的
> （1.5s 与 3s 来回穿插），不是区域结构，每段都 ~0.5、切几段都降不下去。
> 正确做法是给"过长乐段"加软惩罚，让 DP 在 cutability 最高的切点（长镜头边界）
> 自动换曲 —— 修复后同样输入切成 3 段（42.7/22.1/31.9s），边界 cutability 0.98/0.99。

**段时长直接来自镜头**：
```js
seg.dur = shots[i-1].t1 - shots[j].t0;   // 覆盖的镜头之和，不涉及任何比例分配
```

**节奏参数由视频自己推出来**（"视频把控节奏"的落点，2026-10-16 加入）：

| 参数 | 公式 | 效果 |
|---|---|---|
| 乐段上限 `idealMaxSeg` | `clamp(ASL × 15 × (1 − 0.25·能量), 25, 60)` | 快剪片上限 25s、换曲更勤；长镜头慢片放宽到 60s |
| 最短乐段 `minSeg` | `clamp(ASL × 2.5, 4, MIN_SEG)` | 快剪片允许更短的乐段；慢片保持 6s |
| 交叉宽度 `fadeWidthOf` | `clamp(min(前,后段)×0.6, 1.5, 4)` | 短段短交叉，长镜头长交叉 |

### M8 候选曲的裁剪（每首各记各的，2026-10-16 新增）

用户要求：「右侧 ④ 面板点哪首音乐就剪哪首」。裁剪参数因此挂在**候选曲**对象上而非乐段上：

```js
candCut(c, seg) = { start: c.srcStart ?? 2, dur: c.srcDur ?? seg.dur, manual: ... }
segCut(seg)     = candCut(seg.candidates[seg.track], seg)      // 当前选中那首
buildOrder(seg) = [选中的那首, ...其余按分数]                    // 取素材的次序
```

- 同一段里 `[0]` 剪 20s、`[3]` 剪 35s 互不干扰，来回切不覆盖；行尾 ✂ 徽标显示已剪参数
- **修掉一个隐性 bug**：旧版 `buildSegmentBuffer` 永远从 `candidates[0]` 取素材 ——
  用户点了第 3 首、试听也对，但**导出用的还是第 1 首**。现在由 `buildOrder` 保证选中曲优先。
- `renderBGM` 的段长、`buildSegmentBuffer` 的取用起点，统一走 `segCut`，UI 与导出不再各算各的。

### M9 选曲多样性（跨集去重 / 音效过滤 / 艺人打散，2026-10-16 新增）

**问题**：用户实测「试了几集，每集都有重复的音乐，重复性太高了」。

**根因**（`tools/analyze_dup.py` 实测，不是推测）：

| 环节 | 现状 | 后果 |
|---|---|---|
| 情绪档 | 只有 8 个（`MOOD_QUERY`），每档**1 条固定 query 字符串** | 段的 query = 镜头 query 的平均向量 ⇒ 同档的段**逐字节相同** |
| 检索 | `pickTracks` 是纯确定性排序（余弦 + 时长 + BPM + 能量） | 同 query ⇒ 同排序 ⇒ **同一批曲子**，与具体剧情无关 |
| 去重 | `usedSongs` 在每次分析内新建、跨集重置，且只 `add(top[0])` | 每集都从曲库同一个位置开始选 |

模拟 3 集连配（每集 4 段、情绪档序列相同）：

```
现状        → 12 段只用到 4 首曲子，第 1 集与第 2 集选中的 4 首**完全相同**（重复率 67%）
跨集共用池  → 12 段 12 首，重复率 0%
```

曲库侧的两个次要因素（同一脚本统计）：
- **949 首（17.3%）时长 < 12s** —— 是音效素材（`转场.mp3` / `震惊.mp3` / `唰.mp3`），本不该当 BGM
- **艺人聚集**：彭飞 226 首、孟可 120 首、Primary 90 首……同专辑风格极像，连着两首听感就像"同一首放两遍"

**修法（三件事）**：

1. **跨集已用池**（`localStorage` 键 `bgm_used_pool`）

```js
historyPool(videoKey, needCount, libSize) → { set, eps, dropped, total }
videoKeyOf(file) = 文件名 + 粗粒度大小          // 同名同大小视为同一集
rememberEpisode(videoKey, fns)                  // 分析完成 / 导出时覆盖写入
```

- 排除的是**其它集**用过的曲子；**本集旧记录不参与** ⇒ 重跑同一集结果稳定
  （否则用户会遇到"我重跑一次怎么全换了"）
- 曲库余量保护：历史池最多占曲库 `HIST_MAX_FRAC = 45%`，超出则丢弃更早的集，
  保证任何情况下都选得出曲
- UI：复选框「🔁 跨集避免重复用曲」（默认开，可关，开关状态存 `bgm_no_hist`）
  +「🗑 清空配乐记录」+ 实时计数「已记录 N 集 / M 首」
- 导出时会再写一次历史（用户手动换过曲也算数），并检查是否有两段共用了同一首并提示

2. **音效过滤**：`e.dur && e.dur < SONG_MIN_DUR(12)` 直接不入候选
   （`dur` 未知的 39 首不过滤 —— 未知不等于短）

3. **艺人打散**：同一集内已出现过的艺人软扣分 `ARTIST_PENALTY = 0.05`
   —— 够打散（大于情绪项在 top-10 内的差距 0.038），但压不过真正的好匹配；
   `V.A. / 群星 / 合辑 / Various` 不算艺人，避免误伤合集

**边界说明**：这是**行为层的去重**，不改变"同一情绪档的最佳匹配是谁"。
想彻底改变匹配结果（让同档也能命中完全不同的曲子），要么重建索引
（换索引文本模板 / 加"通用度惩罚"字段），要么给每档准备多条 query 轮换 —— 那是另一件事，
当前没做，留作后续选项。

### M5 选曲打分（四维，本方案的第二个"镜头时长"落地处）

**先说一个重要发现**：曲库里**已经有**这些字段，但索引里一个都没带。

```
music_db.sqlite / songs 表：
  duration  5815 条非空   ← 时长
  bpm       5815 条非空   ← 节奏
  rms                     ← 能量
  mood        5855 条      ← 形如「中速/中能量/暗沉」= 速度 / 能量 / 调性
```

实测分布（对本功能很关键）：
- **时长**：`<15s` **1030 首** ｜ 15–30s 144 ｜ 30–60s 394 ｜ 60–120s 1535 ｜ 120–240s 2184 ｜ >240s 528
  → 有 1030 首 15 秒以内的短素材，正好适配短视频快剪段落
- **BPM**：<60 共 103 · 60–80 共 265 · 80–100 共 1165 · 100–120 共 1558 · 120–140 共 1149 · 140–200 共 1350
- **速度/能量/调性**：中速 2173 / 快节奏 3184 / 慢节奏 458；中能量 2498 / 低 1816 / 高 1501；暗沉 2920 / 中性 1168 / 明亮 1081 / 欢快 199 / 抒情 107 / 悬疑 79 / 紧张 77 / 燃 76

**打分公式**

```js
score = w1·cos(情绪向量)          // 现有能力，权重 0.45
      + w2·durFit(曲目时长, 段时长) // 权重 0.25
      + w3·bpmFit(曲目bpm,  段节奏) // 权重 0.20
      + w4·engFit(曲目能量, 段能量) // 权重 0.10
```

**时长匹配 durFit**（用户明确要的）
```js
// 偏好「曲子够长、不用变速」：够长 → 1.0；短一点点 → 允许 loop，小惩罚；差太多 → 0
function durFit(songDur, segDur) {
  if (songDur >= segDur) return 1 - Math.min(0.15, (songDur - segDur) / segDur * 0.15);
  if (songDur >= segDur * 0.6) return 0.7;      // 可 loop 一次
  return Math.max(0, songDur / segDur * 0.5);
}
```

**节奏匹配 bpmFit —— 这就是"用镜头时长配乐"的核心**
```js
// ASL 反推风格档：快剪配快节奏，长镜头配舒缓
const asl = seg.dur / seg.shotCount;             // 该乐段的平均镜头时长
const wantBpm = clamp(60 * 30 / (asl * 10), 70, 150);   // ASL 越小 → 目标 BPM 越高
function bpmFit(bpm, want) { return 1 - Math.min(1, Math.abs(bpm - want) / 60); }
```
直觉：3 秒一切（ASL=3）→ 目标 ~90–110 BPM；0.8 秒一切 → 目标 130–150 BPM；15 秒长镜头 → 目标 70 BPM 铺底。

**能量匹配 engFit**：`mood` 的"低/中/高能量"映射到 0/0.5/1，与乐段情绪强度比较。

**硬约束保留**：无人声（`voc`）、已用不重复、相邻段不同曲。

**性能**：实测单轮全量打分（5459 首 × 1024 维，Node 忠实复刻前端算法）= **168 ms**。8 个乐段 ≈ 1.3 s，**不是瓶颈**。
仍建议加一个**预解码缓存**（`EMB_DECODED`，首次解码后缓存），把 8 轮降到 1 轮解码 + 8 轮点积。

### M6 拼接（改造点：换曲点吸附）

- 换曲/交叉淡入的**中心时刻强制对齐到镜头切点**（V2 已保证边界即切点）
- 仍用等功率交叉 `g_in = sin(πt/2)`、`g_out = cos(πt/2)`
- 交叉时长**自适应**：`C = clamp(min(prev.dur, next.dur) * 0.6, 1.5, 4.0)`
  —— 快切处用短交叉（1.5s），长镜头处用长交叉（4s），不会"糊"掉快剪节奏
- 能量归一化 `TARGET_RMS = 0.12`、放大上限 3.0，防爆音
- 最终 `alignToDuration` 误差 ≤ 0.5s

### M7 剧本规则兜底（成体系）

规则层**不是备胎，是地基**：先算、永远有结果、任何一步失败都不影响它。

| 规则子模块 | 内容 | 产出 |
|---|---|---|
| **情绪词典** | 愤怒/悲伤/悬疑/甜宠/搞笑/燃/压抑 等词表 + 强度权重 | `{mood, intensity}` |
| **台词关键词** | 「跪下」「打脸」「离婚」「重生」「回忆」「三年后」等剧作标记词 | 情绪/结构事件 |
| **结构线索** | 场号变化、出场人物增减、对白密度（字数/秒） | 情绪转折点 |
| **节奏线索** | CPM（镜头数/分钟）、ASL、镜头时长方差 | 能量档位（快/中/慢） |
| **人物线索** | 从剧本抽取主角名，优先用主角相关台词判情绪（Leitmotif） | 情绪主体校正 |

**降级链（任一环失败自动下沉）**
```
VLM 看图成功 ──► 用 VLM query
      │ 失败
      ▼
规则层关键词命中 ──► 用规则 query
      │ 未命中
      ▼
场号/结构推断 ──► 用上一镜头的情绪（情绪延续）
      │ 仍无
      ▼
全局默认情绪（中性铺底）
```
每一层都在 UI 上标注来源（`AI` / `规则` / `延续` / `默认`），可解释、可人工覆盖。

## 六、性能：为什么"更新后变慢"，以及怎么救回来

### 实测数据（都是本机真跑出来的，不是估算）

| 环节 | 实测 | 结论 |
|---|---|---|
| 选曲打分（5459 首 × 1024 维，一轮全量） | **168 ms** | 8 段 ≈ 1.3s，**不慢** |
| 镜头抽帧 seek（640×360 webm） | **21 ms / 次** | 88.8s 视频 148 次 ≈ **3.1 s**，**不是主因** |

**新旧版本的 `analyzeBtn` 循环代码逐行 diff = 完全一致**（除 `vlAllFailed` 判断）。所以本地计算侧没有回归。

### 真正的"变慢"来源

改动**只有一处会影响耗时**，而且它是修 bug 的必然代价：

| | 修复前 | 修复后 |
|---|---|---|
| AI 看图模型 | `qwen-vl-flash` — **不存在** ⇒ 服务端**秒回 404** | 真实存在的 Qwen3-VL ⇒ **真的上传图片 + 视觉推理** |
| 每段耗时 | ~0.3s（失败返回） | **1~5s**（视觉推理） |
| 12 段合计 | ~4s（但结果全是规则兜底出来的） | **12~60s**（结果是真的 AI 看图） |

**结论**：不是代码变慢，是**AI 看图从"假装在工作"变成"真的在工作"**。以前那 4 秒换来的是 12 段全部降级成规则兜底。

叠加第二个因素：**候选链降级**。如果你的账号没有 `qwen3.8-flash`，第一段会依次试 2~8 个模型（每次都一个完整往返），只有第一段付这个成本，命中后本次会话固定复用。

### 优化清单（按收益排序）

| # | 优化 | 做法 | 预期 |
|---|---|---|---|
| 1 | **VLM 并发** | 4 路并发池替代串行 | 12 段串行 → **3 批**，快 ~4× |
| 2 | **减少 VLM 调用** | 只对"关键镜头"（最长 K 个 + 情绪突变 + 均匀采样）调用，其余走规则 | 12 次 → **~6 次** |
| 3 | **抽帧封顶** | `STEP = clamp(dur/160, 0.4, 1.5)` | 长视频不再线性变慢 |
| 4 | **预解码缓存** | `EMB_DECODED` 首次解一次，后续只算点积 | 打分 8×168ms → **168ms + 8×点积** |
| 5 | **两段式召回** | int8 字节粗排 top-200 → 解码精排 | 打分再快 ~5× |
| 6 | **进度可见** | 每段显示"AI看图 x/y（并发 4）"，并给预估剩余时间 | 体感问题往往就是"没有反馈" |

> 顺带一句：如果只想**快**，最彻底的办法是**关掉 AI 看图**（留空「👁 看图模型」并勾选"仅用规则"），走纯规则兜底 —— 全片几秒出结果，效果取决于 M7 规则表的质量。

| 维度 | V1 | V2 |
